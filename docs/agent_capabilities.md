# Agent capabilities and remaining limits

Audited against the local implementation on 14 October 2026, including the integration hardening changes. These describe code capabilities, not a claim that real models or hosted services have passed acceptance testing.

## What runs now

The application connects two workflows:

- Documents: upload → parser → extraction → graph memory evolution → Neo4j and Chroma indexing.
- Questions: query plan → graph/vector retrieval → reasoning → critic → cited answer or an insufficient-evidence response.

Extraction, graph, query, reasoning, and critic agents already use the shared LLM client. A separate additional “LLM agent” is unnecessary. The parser, orchestration, and retrieval perform deterministic processing and database operations around those models.

| Availability | Meaning |
|---|---|
| Offline demo | Available without credentials. Uses narrow scripted extraction, keyword search, and quoted passages. It demonstrates the workflow; it cannot establish AI answer quality. Its persistent data lives separately under `data/demo`. |
| Full Neo4j + Chroma pipeline | Implemented. Requires real model credentials and a local Neo4j or Aura connection. Live Cypher/API compatibility and answer quality still need testing in your environment. |
| OCR | Optional, enabled with `PARSER_ENABLE_OCR=1`. Requires the Tesseract executable and suitable language data. Applies to missing text pages in mixed or fully scanned PDFs. |
| Figure descriptions | Optional parser API only: enable the figure configuration and provide `describe_image(bytes) -> str`. The standard UI supplies no vision callback. |
| External web information | Reasoning API supports an opt-in pluggable search function. No search service is configured by default, and document chat does not enable external search. |
| Team sign-in | Implemented OIDC access gate with verified-email allowlist. Requires real identity-provider secrets and integration testing. All authorized team members share the same document workspace. |

## Every agent

| Agent or component | Implemented capabilities | Remaining limits |
|---|---|---|
| **Document parser** | Reads TXT, Markdown, text PDFs, DOCX, CSV, and XLSX; validates file type, 20 MB input limit, encryption, and Office ZIP expansion/member limits; hashes sources; removes common formatting noise and boilerplate; identifies sections; chunks prose and tables with bounded prose overlap; flags numeric tables; records PDF prose page numbers; carries section headings across PDF pages; marks OCR text by its originating page; optional raster-figure descriptions. | No audio, video, PPT, or general website ingestion. Complex columns, reading order, merged cells, charts, and OCR accuracy remain imperfect. Text, tables, and figures are emitted in separate groups rather than reconstructed document order. Page-spanning tables retain the first page citation. DOCX has no reliable physical pages. XLSX uses stored formula results and does not calculate formulas. Tables retain at most 500 body rows with a warning. Plain-heading recognition is heuristic; short title-like facts can remain ambiguous. |
| **Ingestion pipeline** | Combines parsing, extraction, graph writing, and indexing; detects duplicate document hashes; requires explicit replacement for changed content under the same filename stem; preserves previous data after empty/failed replacement; detects source changes during parsing; reports per-chunk failures; commits a document graph in one batch; stores recoverable vector upserts and exact old-note cleanup work; supports retrying indexing. Slow parsing/extraction occurs outside the graph read lock. | Filename stem is still document identity, so distinct files named alike share an identity. No background job queue, ingestion cancellation, scheduled connectors, or multi-worker coordination. A first ingestion can be partial when some chunks fail. Graph and vector stores do not share one transaction; semantic search may temporarily lag committed facts. Parser warnings are logging output, not a completeness guarantee. |
| **Extraction agent** | Creates stable provenance-preserving notes; extracts entities from eight agreed types, free-form snake_case relationships, keywords, tags, summary, and title; requires valid types, unique entity names, known relation endpoints, exact source quotes, and timezone-aware event timestamps; rejects extracted knowledge on notes marked uninformative; repairs invalid outputs once; includes document and conversation APIs. | Exact quotes and schema validation do not prove that a relation, summary, or event time is semantically correct. Cross-chunk pronouns/coreference and arbitrary domain terminology are not guaranteed. It has no fixed relation ontology. Secret exclusion is a prompt instruction, not a deterministic redaction system. Conversation API exists, but UI chat turns are not automatically added as permanent knowledge. |
| **Graph agent** | Resolves exact entities and aliases; uses bounded model-assisted identity candidates; adds, merges, retains, retires, or updates memory; preserves sources, revisions, and audit decisions; rejects unknown targets; checks equivalent facts before consolidation; requires explicitly later event times and configured single-valued predicates before supersession; marks index work for retry; batches vector writes. | Entity identity and model proposals remain fallible. Defaults treat only `managed_by` and `led_by` as single-valued. Updates operate on whole notes, so mixed facts are handled conservatively. No general historical/as-of question support, ontology management, or graph-quality guarantee. Corpus state still loads into Python memory. |
| **Query agent** | Normalizes Unicode, controls, whitespace, and question length; requests typo/shorthand correction and a standalone question; uses bounded recent history to resolve references; identifies up to ten target entities; selects graph, vector, or hybrid retrieval; validates returned fields and falls back to a deterministic hybrid plan when the model fails. | A rewrite can still change meaning or resolve an ambiguous reference incorrectly. Entity checks reduce invented anchors but cannot establish semantic equivalence. No autonomous search program, persistent conversation memory, or guaranteed multilingual planning. The planner uses only a small history window. |
| **Retrieval agent** | Retrieves active graph relationships and semantic passages; follows aliases; selects configurable graph depth, fact cap, top-k, and similarity threshold; filters invalid, duplicate, unsupported-source, and stale results; overfetches before active-note filtering; prioritizes the original passages behind graph facts; falls back to vectors when graph retrieval is empty; attaches evidence IDs and source provenance. | No learned reranker or rank fusion. Recall depends on entity resolution, embeddings, thresholds, and bounded result budgets. Graph traversal is an in-memory operation. There is no per-user or per-document permission filter: the configured workspace is shared. It cannot guarantee that all relevant sources were retrieved. |
| **Reasoning agent** | Analyzes question type and subquestions; generates structured explicit/derived claims, citations, missing information, conflicts, temporal checks, and a readable answer; applies evidence-size budgets; validates evidence IDs and date/number support; repairs invalid structured answers; derives state and heuristic confidence in code; degrades safely after model failures; optional external merge/verification through a supplied search backend. | It cannot guarantee truth, completeness, or arithmetic/inference correctness. Confidence is a rule-based score, not a calibrated probability. There is no calculator, executable tool workflow, or comprehensive cross-document conflict detection. External searches require explicit permission and a backend; default document answers use uploaded evidence only. |
| **Critic agent** | Checks schema consistency, known citations, source labeling, explicit dates/numbers, and factual support; uses a model to audit the entire displayed answer against cited evidence; requests broader retrieval and feedback-driven regeneration; stops after at most two retries; unsupported answers are withheld while valid partial answers remain visible. | Model review can still miss subtle errors or reject a valid answer. It cannot verify the original source’s truth. The legacy `assess()` method only counts evidence; orchestration uses the stronger `review_answer()` path. |
| **Shared LLM client** | Supports OpenAI and Anthropic adapters, separate per-agent provider/model settings, scripted test providers, JSON parsing/repair, reusable SDK clients, bounded timeout/SDK retries, client cleanup, and thread-local token/call/timing counters. Custom providers can be registered. | Real-provider smoke testing remains required. Not every model accepts the configured chat/JSON/token/temperature options. No default local-model server, vision, streaming UI, model-quality evaluation, or monetary cost calculation is supplied. SDK retries may make more provider requests than the displayed logical call count. |

## Stores, interface, and evaluation

| Component | Implemented capabilities | Remaining limits |
|---|---|---|
| **Neo4j store** | Local and Aura configuration; transactional state plus graph projection; fixed parameterized relationship writes; graph namespace, uniqueness constraints, revision checks, and source relationships; updates only changed projection records; skips unchanged commits. | Retains a complete serialized corpus snapshot and refreshes it into Python. Projection changes are incremental, but the state payload is not. Revision conflicts are detected rather than silently overwritten; multi-worker scale needs a different transaction/traversal design. A namespace is not authorization. Live server behavior needs verification. |
| **Chroma store** | Persistent local semantic index, explicitly selected embedding function, cosine scores, idempotent batched upserts, exact note deletion, and recoverable indexing after outages. Runtime uses local `all-MiniLM-L6-v2` embeddings. | Embedding weights may download on first use. Changing embeddings requires a compatible new collection and reingestion. Local persistent Chroma needs backed-up storage and deployment-specific concurrency evaluation. No relevance guarantee or per-user access control. |
| **Upload/chat UI** | Uploads multiple supported documents with bounded count/size; explicit replacement; ingestion reports; sample demo; indexing retry; cited sources and pages; session chat and bounded history; confidence, latency, and model-usage display; optional team login/logout. | Chat is session state rather than a saved conversation service. No streaming, background ingestion, graph editor, document-management UI, or public per-user isolation. The team workspace intentionally shares documents. OIDC and hosted runtime configuration require testing. |
| **CLI and evaluation** | Headless ingestion/questions/service checks; numbered/plain-text questions and annotated JSONL cases; answer-term, source-document, and abstention checks; error reporting plus median/p95 observed latency. | Annotation checks are explicit heuristics, not semantic accuracy. A useful acceptance suite needs representative ground truth and manual support reviews. A database connectivity check alone does not establish model, embedding, or end-to-end readiness. |

## What the hardening changes improve

Parser changes preserve PDF pages, process mixed scanned PDFs, retain short unpunctuated assertions, avoid incorrect unknown-image filtering, enforce expanded Office limits, cap prose overlap, and avoid materializing discarded CSV/XLSX rows. Integration changes batch document commits and embeddings, recover failed vector cleanup, preserve merged sources, update changed Neo4j projection records, release graph locks during answer generation, expose retrieval controls and usage/timing, and add an optional team access gate.

This improves the local/team version. It does not certify all possible documents, all models, or large public deployments. Run the concrete checks in [the deployment checklist](deployment_checklist.md), and use annotated real documents to decide whether the quality and performance meet your deployment target.
